## คืออะไร

การใช้ Claude Code ส่วนใหญ่คือหนึ่งเซสชัน หนึ่ง context window [Subagents](/docs/subagents)
ขยายจากภายในเซสชันนั้น — agent หลักมอบหมายงานย่อยให้ตัวช่วยที่รายงานสรุปกลับมาแล้วก็หายไป
หน้านี้พูดถึงระดับถัดไป: **การรัน Claude Code หลายเซสชันที่เป็นอิสระจากกันบนงานชิ้นเดียวกัน
พร้อมกัน** แล้วให้พวกมันประสานงานกัน

มีสองวิธีที่เกิดขึ้นได้จริง และควรแยกให้ชัด:

1. **Agent teams** — ฟีเจอร์ทดลอง (experimental) ที่มีชื่อเป็นทางการของ Claude Code หนึ่งเซสชัน
   (**lead**) จะ spawn เซสชัน Claude Code เต็มรูปแบบอื่นๆ (**teammates**) โดยแต่ละตัวมี context
   window ของตัวเอง พวกมันแชร์ task list ร่วมกัน, จับงานเอง, และส่งข้อความหากันโดยตรง — lead
   ไม่ต้องคอย relay ทุกอย่าง
2. **การรันหลายเซสชันแบบ manual** — ไม่มีฟีเจอร์พิเศษเลย แค่คุณเปิดหลาย terminal (หรือ
   [tmux](/docs/tmux) panes) แล้วรัน `claude` ในแต่ละอัน โดยทั่วไปคือหนึ่งเซสชันต่อหนึ่ง
   [git worktree](https://git-scm.com/docs/git-worktree) เพื่อไม่ให้เซสชันชนกันบนไฟล์ Claude
   Code รองรับวิธีนี้โดยตรงด้วย `claude --worktree <name>`

ทั้งสองแบบถือเป็น "agent teams" ในความหมายกว้างๆ ของวลีนี้ แต่มีแค่แบบแรกเท่านั้นที่เป็นฟีเจอร์
ผลิตภัณฑ์เฉพาะที่ใช้ชื่อนี้ และยังเป็น experimental อยู่ — อยู่หลัง flag เปลี่ยนแปลงได้ตลอด
และมีข้อจำกัดที่บันทึกไว้แล้วเรื่องการ resume เซสชันและการปิดระบบ ส่วนที่เหลือของหน้านี้จะครอบคลุม
ทั้งสองแบบ และบอกชัดเจนว่ากำลังพูดถึงแบบไหน

<Note title="นี่ไม่เหมือนกับ Subagents" type="default">
  [Subagents](/docs/subagents) รัน *ภายใน* โปรเซสของเซสชันเดียว รายงานผลกลับไปยังผู้เรียกคนเดียวนั้น
  และคุยกันเองไม่ได้ Agent teams คือโปรเซส Claude Code แยกกัน แต่ละตัวมี context เป็นอิสระ
  ที่ส่งข้อความหากันโดยตรงและแชร์ task list ถ้า worker ของคุณแค่ต้องรายงานกลับมาหาคุณ subagents
  จะง่ายกว่าและถูกกว่ามากในแง่ token ให้เลือกใช้ team เมื่อ worker ต้องประสานงาน *กันเอง*
  ไม่ใช่แค่กับคุณ
</Note>

## Subagents กับ agent teams ต่างกันอย่างไร

| | Subagents | Agent teams |
|---|---|---|
| **โปรเซส** | รันภายในเซสชันของผู้เรียก | เซสชัน Claude Code แยกต่างหากต่อ teammate หนึ่งคน |
| **Context** | มี context window ของตัวเอง ส่งสรุปกลับให้ผู้เรียก | มี context window ของตัวเอง เป็นอิสระเต็มรูปแบบ |
| **การสื่อสาร** | รายงานกลับให้ agent หลักเท่านั้น | teammates ส่งข้อความหากันโดยตรง |
| **การประสานงาน** | agent หลักจัดการการมอบหมายทั้งหมด | มี task list ที่แชร์กัน teammates จับงานเอง |
| **ต้นทุน token** | ต่ำกว่า — งานส่วนใหญ่ถูกสรุปทิ้งไป | สูงกว่า — teammate แต่ละตัวคือ Claude เต็มรูปแบบ |
| **เหมาะกับ** | งานย่อยที่โฟกัสเดียว ซึ่งสนใจแค่ผลลัพธ์ | งานที่ได้ประโยชน์จากการถกเถียงหรือการสำรวจแบบขนานที่เป็นอิสระ |

## วิธีใช้

### ฟีเจอร์ในตัว

Agent teams มาพร้อม flag แบบ experimental เปิดใช้งานได้ใน `settings.json`:

```json title="~/.claude/settings.json"
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

เมื่อเปิดใช้งานแล้ว ให้ขอ team เป็นภาษาธรรมดา แล้ว Claude จะ spawn และประสานงานให้เอง:

```text
Spawn three teammates to review this PR:
- one focused on security implications
- one checking performance impact
- one validating test coverage
Have them each review and report findings.
```

Claude จะตัดสินใจเองว่างานนี้ต้องการ teammate กี่คน เว้นแต่คุณจะระบุชัดเจน terminal ของ lead
จะแสดง panel ที่แสดงรายชื่อ teammates อยู่ใต้ prompt; ปุ่มลูกศรใช้เลือก, Enter เปิด transcript
เพื่ออ่านหรือส่งข้อความให้มันโดยตรง, Escape ขัดจังหวะเทิร์นปัจจุบันของมัน

เบื้องหลัง team ถูกสร้างจากสามส่วน:

<Mermaid chart="graph TD
  You[You] -->|describe the task| Lead[Team lead<br/>your main session]
  Lead -->|spawns, assigns tasks| T1[Teammate: security]
  Lead -->|spawns, assigns tasks| T2[Teammate: performance]
  Lead -->|spawns, assigns tasks| T3[Teammate: tests]
  T1 <-.messages.-> T2
  T2 <-.messages.-> T3
  T1 <-.messages.-> T3
  T1 -.claims/updates.-> Tasks[(Shared task list)]
  T2 -.claims/updates.-> Tasks
  T3 -.claims/updates.-> Tasks" />

- **Task list** — งานที่ pending / in-progress / completed บางงานมี dependency กับงานอื่น
  teammates จะจับงานถัดไปที่ไม่ติด block เองเมื่อทำงานปัจจุบันเสร็จ หรือ lead จะมอบหมายงานให้
  ตรงๆ ก็ได้
- **Mailbox** — teammate แต่ละคนมี inbox ของตัวเอง; การส่งแบบ `SendMessage` เกิดขึ้นอัตโนมัติ
  ดังนั้น lead ไม่ต้องคอย poll เพื่อดูความคืบหน้า เมื่อ teammate ว่างงาน มันจะแจ้ง lead เอง
- **Display mode** — teammates จะรันแบบ **in-process** เป็นค่าเริ่มต้น (ทั้งหมดอยู่ใน terminal
  เดียวของคุณ สลับกันดูผ่าน agent panel) หรือรันแบบ **split panes** หนึ่ง pane ต่อหนึ่ง teammate
  ซึ่งต้องใช้ [tmux](/docs/tmux) หรือ iTerm2 ดู
  [Agent Teams with tmux](/docs/agent-teams-tmux) สำหรับวิธีตั้งค่านั้นแบบเต็ม

มีอีกสองการควบคุมที่ควรรู้:

- **Plan approval** — สำหรับงานที่มีความเสี่ยง ให้ teammate วางแผนก่อนแตะไฟล์: *"Spawn an
  architect teammate to refactor the auth module. Require plan approval before making changes."*
  มันจะทำงานในโหมด plan แบบอ่านอย่างเดียวจนกว่า lead จะอนุมัติ
- **Reusable roles** — teammate สามารถถูก spawn จากนิยาม [subagent](/docs/subagents) ที่ตั้งชื่อไว้
  (ขอบเขตระดับ project, user หรือ plugin) ดังนั้น role อย่าง `security-reviewer` จะทำงานได้ทั้งใน
  ฐานะ on-demand subagent และในฐานะ team role โดยนิยามแค่ครั้งเดียว

### แบบ manual

คุณไม่จำเป็นต้องเปิด flag experimental เพื่อรัน Claude Code หลายเซสชันบนงานเดียว — นี่คือแค่การรัน
`claude` มากกว่าหนึ่งครั้ง โดยตั้งใจแยกให้เป็นอิสระจากกัน:

```bash
claude --worktree feature-auth      # terminal 1: isolated checkout on its own branch
claude --worktree fix-rate-limit    # terminal 2: a second isolated checkout
```

การเรียก `--worktree` แต่ละครั้งจะสร้าง `git worktree` จริงๆ — ไดเรกทอรีการทำงานแยกต่างหาก บน
branch ของตัวเอง checkout มาจาก repository เดียวกัน — ดังนั้นสองเซสชันที่ "แก้ไขโปรเจกต์เดียวกัน"
จะไม่มีวันแก้ไฟล์เดียวกันบนดิสก์เลย นี่คือกลไกที่ [Agent Teams with
tmux](/docs/agent-teams-tmux) ใช้สร้าง layout ที่จับต้องได้: หนึ่ง pane ต่อหนึ่งเซสชัน หนึ่ง
worktree ต่อหนึ่ง pane

แบบ manual จะเสียการมี task list ที่แชร์กันและการส่งข้อความระหว่าง agent ที่ฟีเจอร์ในตัวมีให้ —
คุณคือชั้นของการประสานงานเอง ต้องอ่าน output ของแต่ละเซสชันแล้วตัดสินใจว่าจะทำอะไรต่อ แลกกับสิ่งนี้
คือมันไม่ต้องใช้ flag ใดๆ ไม่มีข้อจำกัดของฟีเจอร์ experimental และ debug ได้ง่ายพอๆ กับการรัน
Claude Code แบบปกติ เพราะมันก็คือแค่นั้นเอง

## เมื่อไหร่ที่คุ้มค่ากับความซับซ้อน

"agent หลายตัว" ทั้งสองรูปแบบมีต้นทุนสูงกว่าหนึ่งเซสชัน: token มากกว่า (teammate แต่ละคนคือ
context window เต็มรูปแบบ), ความสนใจมากกว่า (ต้องมีคนอ่าน output ของแต่ละตัว) และ — สำหรับ
ฟีเจอร์ในตัวโดยเฉพาะ — คุณกำลังเลือกใช้ code path แบบ experimental

มันคุ้มค่าเมื่อ:

- **งานนั้นขนานกันได้จริงและเป็นอิสระต่อกัน** สามคนสามารถทำสามอย่างนี้พร้อมกันได้โดยไม่ต้องคุยกัน
  มาก เช่น โมดูลใหม่, การรีวิวสามมุม security/performance/test, หรือการเปลี่ยนแปลงข้ามเลเยอร์
  (frontend, backend, tests) ที่แต่ละ worker เป็นเจ้าของ
- **สมมติฐานที่แข่งกันดีกว่าการสืบสวนเดียว** agent ตัวเดียว (เหมือนวิศวกรคนเดียว) มักจะยึดติดกับ
  ทฤษฎีแรกที่ดูเป็นไปได้ agent หลายตัวที่สืบสวนบั๊กเดียวกันอย่างอิสระ และพยายามหักล้างกันเองอย่าง
  จริงจัง จะเจอต้นตอที่แท้จริงได้เร็วกว่า agent ตัวเดียวที่ไล่ตามทางเดียว
- **คุณต้องการการรีวิวจากหลายมุมมองบนชิ้นงานเดียวกัน** ผู้รีวิวคนเดียวมักโฟกัสประเด็นเดียวใน
  ครั้งหนึ่ง ผู้รีวิวสามคนที่มีสามภารกิจต่างกันจะจับปัญหาได้มากกว่า พร้อมกัน มากกว่าผู้รีวิวคนเดียว
  ที่จับสามอย่างตามลำดับ

มันไม่คุ้มค่า — subagents ธรรมดาหรือเซสชันเดียวใช้ได้ดีกว่า — เมื่อ:

- **งานเป็นลำดับหรือมี dependency หนัก** ถ้าขั้นตอนที่ 2 ต้องใช้ output ของขั้นตอนที่ 1
  teammates จะใช้เวลาส่วนใหญ่รอหรือประสานงานกันใหม่ และคุณก็จ่ายค่า parallelism ที่ใช้ไม่ได้จริง
- **worker หลายตัวจะแตะไฟล์เดียวกัน** สอง agent แก้ไฟล์เดียวกันคือตัวสร้างความขัดแย้ง ไม่ใช่ตัวเร่ง
  ความเร็ว — เรื่องนี้ใช้ได้ไม่ว่าจะเป็น subagent สองตัว, teammate สองตัว หรือคนสองคน
- **มันคืองานประจำที่เซสชันเดียวจัดการได้สบายอยู่แล้ว** overhead การประสานงาน (การ spawn, การส่งต่อ
  งาน, การสังเคราะห์ผลลัพธ์) ไม่ได้ฟรีแม้ไม่ก่อให้เกิดความขัดแย้งก็ตาม ให้ใช้ team เมื่อการสำรวจ
  แบบขนานคือประเด็นหลัก ไม่ใช่เป็นค่าเริ่มต้น

## แนวปฏิบัติที่ดี

- **เริ่มจากงานวิจัยและรีวิว ไม่ใช่การ implement** ถ้าคุณยังใหม่กับเรื่องนี้ การรีวิว PR จากสามมุม
  มีขอบเขตงานที่ชัดเจนและความเสี่ยงชนกันต่ำ ในขณะที่การเขียนโค้ดแบบขนานมีทั้งสองปัญหา
- **ให้ context จริงกับแต่ละ teammate ใน spawn prompt** teammates จะโหลด `CLAUDE.md`, skills และ
  MCP servers อัตโนมัติ แต่ไม่โหลดประวัติบทสนทนาของ lead — บอกสิ่งที่คุณจะบอกพนักงานใหม่ที่เพิ่ง
  เข้ามารับงานแบบไม่มีข้อมูลเลย
- **ปรับขนาด team ให้เหมาะกับงาน ไม่ใช่ให้เต็มเพดาน** สามถึงห้า teammates เป็นช่วงที่สมเหตุสมผล
  สำหรับงานส่วนใหญ่ teammate ที่มากกว่านี้จะเพิ่ม overhead การประสานงานและต้นทุน token โดยไม่ได้
  ความเร็วเพิ่มขึ้นตามสัดส่วน
- **หนึ่งไฟล์ หนึ่งเจ้าของ** ไม่ว่าจะเป็นฟีเจอร์ในตัวหรือ worktrees แบบ manual ให้ตัดสินใจล่วงหน้าว่า
  ใครเป็นเจ้าของไฟล์หรือโมดูลไหน เพื่อไม่ให้มีใครเขียนทับการแก้ไขของคนอื่น
- **ตามงานอย่างต่อเนื่อง** เช็คความคืบหน้า ปรับทิศทางที่หลงทาง และสังเคราะห์ผลลัพธ์ทันทีที่มาถึง
  แทนที่จะปล่อยทิ้งไว้เป็นชั่วโมง team ที่ไม่มีคนดูแลแล้ววิ่งผิดทางเป็นเวลานานมีต้นทุนสูงในแบบที่
  เซสชันเดียวที่ไม่มีคนดูแลมักจะไม่เป็น
- **เลือก subagents เมื่อ worker ไม่ต้องคุยกันเอง** ถ้าช่องทางสื่อสารที่คุณต้องการคือแค่ "worker
  รายงานกลับมาหาฉัน" นั่นคือเครื่องมือที่ถูกกว่าและง่ายกว่า — ดู [Subagents](/docs/subagents)
