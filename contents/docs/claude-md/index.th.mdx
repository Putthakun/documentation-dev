## คืออะไร

ทุกเซสชันของ Claude Code เริ่มต้นด้วย context window ว่างเปล่า — ไม่มีความจำจากเซสชันเมื่อวานติด
มาเองเลย `CLAUDE.md` คือวิธีที่คุณให้คำสั่งที่คงอยู่ถาวรได้อยู่ดี: ไฟล์ markdown ธรรมดา ที่โหลดใหม่
ทุกครั้งเมื่อเซสชันเริ่มต้น ซึ่ง Claude ปฏิบัติเหมือนเป็น context มากกว่า configuration ที่บังคับใช้
`AGENTS.md` ของ repo นี้เอง (ที่ `CLAUDE.md` ที่ root import เข้ามา) ก็คือกลไกนี้ที่ถูกใช้งานจริง —
กฎเรื่อง sidebar ที่ไม่ใช่อัตโนมัติ, การใส่ prefix `/docs` บน Card hrefs, และ convention เรื่องรูป
แบบของแต่ละ section ล้วนอยู่ในไฟล์นั้นเพราะเป็นสิ่งที่ควรพูดซ้ำทุกเซสชัน แทนที่จะให้ค้นพบเองผ่านการ
ลองผิดลองถูก

Claude Code ยังมีระบบความจำที่สอง แยกต่างหาก: **auto memory** คือโน้ตที่ Claude เขียนถึงตัวเองไว้ที่
`~/.claude/projects/<project>/memory/` โดยอิงจากการแก้ไขที่คุณให้ระหว่างเซสชัน CLAUDE.md คือสิ่งที่
*คุณ* เขียน; auto memory คือสิ่งที่ *Claude* เขียน ทั้งสองอย่างโหลดทุกเซสชัน หน้านี้พูดถึงอันที่คุณ
ควบคุมโดยตรง

## มันโหลดอย่างไร

ไฟล์ CLAUDE.md มีอยู่หลายระดับ โหลดตามลำดับนี้ — จากกว้างสุดไปเฉพาะเจาะจงสุด ดังนั้นคำสั่งระดับ
โปรเจกต์จึงเป็นสิ่งสุดท้าย (และเน้นย้ำที่สุด) ที่ Claude อ่าน:

| ระดับ | ตำแหน่ง | แชร์กับ |
|---|---|---|
| นโยบายที่จัดการโดยองค์กร | `/etc/claude-code/CLAUDE.md` (Linux), หรือเทียบเท่าบนแพลตฟอร์มอื่น | ทุกคนในเครื่อง บังคับใช้โดย IT |
| ผู้ใช้ | `~/.claude/CLAUDE.md` | เฉพาะคุณ ในทุกโปรเจกต์ |
| โปรเจกต์ | `./CLAUDE.md` หรือ `./.claude/CLAUDE.md` | ทั้งทีม ผ่าน git |
| ท้องถิ่น | `./CLAUDE.local.md` | เฉพาะคุณ โปรเจกต์นี้ — อยู่ใน gitignore |

Claude Code จะไล่ขึ้นจากไดเรกทอรีการทำงานของคุณ โหลด `CLAUDE.md` และ `CLAUDE.local.md` จากทุก
ไดเรกทอรีที่ผ่าน ไฟล์ที่ repo root จะโหลดเต็มตอนเริ่มระบบ; ไฟล์ `CLAUDE.md` ใน *ไดเรกทอรีย่อย* จะ
โหลดก็ต่อเมื่อ Claude อ่านไฟล์ในไดเรกทอรีย่อยนั้นจริงๆ — มันจะไม่ถูกดึงเข้า context แค่เพราะมันมี
อยู่ ภายในไดเรกทอรีเดียวกัน `CLAUDE.local.md` จะโหลดหลัง `CLAUDE.md` ดังนั้นโน้ตส่วนตัวของคุณจึงเป็น
สิ่งสุดท้ายที่ถูกอ่านในระดับนั้น

  B --> C[Project ./CLAUDE.md]
  C --> D[Project CLAUDE.local.md]
  D --> E[Session context]
  F[Nested dir CLAUDE.md] -.->|loaded only when Claude<br/>reads a file there| E" />

รัน `/context` ในเซสชันเพื่อดูรายละเอียดว่าไฟล์ memory ไหนถูกโหลดจริง — วิธีที่เร็วที่สุดในการ
ยืนยันว่าไฟล์ที่คุณเพิ่งเพิ่มถูกอ่านเข้าไปแล้ว

## Imports ด้วย `@path`

CLAUDE.md สามารถดึงไฟล์อื่นเข้ามาด้วย `@path/to/file`:

```markdown
See @README for project overview and @package.json for available npm commands.

# Additional Instructions
- git workflow: @docs/git-instructions.md
```

ไฟล์ที่ import จะถูกขยายเข้า context ตอนเริ่มระบบ พร้อมกับไฟล์ที่อ้างอิงถึงมัน และสามารถ import
ซ้อนกันได้ลึกสุดสี่ชั้น การครอบ path ด้วย backtick (`` `@README` ``) จะทำให้มันเป็นข้อความล้วนแทนที่
จะไปทริกเกอร์การ import — มีประโยชน์เมื่อคุณแค่อยาก *กล่าวถึง* path เฉยๆ

นี่คือวิธีที่ `CLAUDE.md` ที่ root ของโปรเจกต์นี้ทำงานพอดี: มันคือการ import `@AGENTS.md` แค่บรรทัด
เดียว ดังนั้นคำสั่งจริงๆ จึงอยู่ในไฟล์ที่เครื่องมืออื่น (หรือมนุษย์) อ่านได้โดยตรง แล้ว Claude Code
ก็แค่ดึงมันเข้ามา รูปแบบนั้น — `@AGENTS.md` บวกกับส่วนเสริมเฉพาะ Claude ด้านล่างมัน — คือวิธีที่
แนะนำสำหรับการแชร์ไฟล์คำสั่งเดียวข้ามเครื่องมือ AI coding หลายตัว:

```markdown title="CLAUDE.md"
@AGENTS.md

## Claude Code

Use plan mode for changes under src/billing/.
```

<Note type="warning">
  การ import ที่ resolve ออกไป *นอก* working directory ของคุณ (เช่น `@~/.claude/my-notes.md`
  จากไฟล์โปรเจกต์) จะถูกถือว่าเป็น external และทริกเกอร์ dialog อนุมัติแบบครั้งเดียวในครั้งแรกที่
  Claude Code เจอมัน — เพราะอาจมีคนอื่น commit ไฟล์โปรเจกต์ที่ import สิ่งที่ไม่คาดคิดไว้ก็ได้
  การ import ในไฟล์ระดับ user-scope ของคุณเองจะไม่ถามเลย
</Note>

## `/memory` และการแก้ปัญหา

`/memory` จะแสดงรายการตำแหน่ง CLAUDE.md และ CLAUDE.local.md ทุกระดับ — รวมถึงตำแหน่งที่ยังไม่มี
ไฟล์อยู่ด้วย — และเปิดไฟล์ที่คุณเลือกในตัวแก้ไขของคุณ ถ้า Claude ไม่ทำตามคำสั่ง:

1. รัน `/context` และเช็ครายการ **Memory files** — ถ้าไฟล์ไม่อยู่ในนั้น แปลว่า Claude ไม่เคยเห็น
   มันเลย
2. เช็คว่ามันอยู่ในตำแหน่งที่โหลดจริงสำหรับเซสชันนี้ (ดูตารางด้านบน)
3. ทำให้คำสั่งเฉพาะเจาะจงมากขึ้น "Use 2-space indentation" จะถูกทำตามได้แม่นยำกว่า "format code
   nicely" มาก — CLAUDE.md คือ context ที่ Claude *พยายาม* ทำตาม ไม่ใช่ configuration ที่บังคับ
   ใช้ ดังนั้นความเฉพาะเจาะจงจึงเป็นตัวตัดสินการทำตามจริง
4. มองหาความขัดแย้งข้ามไฟล์ ไฟล์ CLAUDE.md สองไฟล์ที่ให้คำแนะนำต่างกันสำหรับเรื่องเดียวกัน หมายความ
   ว่า Claude จะเลือกอันใดอันหนึ่งแบบสุ่ม

เนื้อหา CLAUDE.md ยังคงอยู่รอด `/compact`: ไฟล์ที่ root ของโปรเจกต์จะถูกอ่านใหม่จากดิสก์และฉีดกลับ
เข้าไปหลังทุกการ compact ไฟล์ CLAUDE.md ที่ซ้อนอยู่ในไดเรกทอรีย่อยและกฎที่จำกัดขอบเขตตาม path จะไม่
ถูกฉีดกลับเข้าไปอัตโนมัติ — พวกมันจะโหลดใหม่ในครั้งถัดไปที่ Claude อ่านไฟล์ที่ตรงกัน

สำหรับสิ่งที่ต้องเกิดขึ้นแน่นอนทุกครั้งไม่ว่า Claude จะตัดสินใจอย่างไร — "รัน linter ก่อน commit
เสมอ", "อย่าให้ไฟล์นี้ถูกแก้ไขเด็ดขาด" — คำสั่งใน CLAUDE.md ไม่ใช่เครื่องมือที่ถูกต้อง มันเป็นคำขอ
ไม่ใช่กลไกบังคับใช้ ใช้ [hook](/docs/hooks) แทน

## แนวปฏิบัติที่ดี

- **ให้สั้นกว่าประมาณ 200 บรรทัด** ไฟล์ที่ยาวกว่านี้ใช้ context มากขึ้นทุกเซสชัน และลดความน่าเชื่อ
  ถือที่ Claude จะทำตามคำสั่งใดๆ ในนั้นอย่างวัดผลได้
- **จดสิ่งที่คุณจะต้องอธิบายซ้ำอยู่ดี** เงื่อนไข trigger ที่ควรจำ: Claude ทำผิดพลาดเดิมซ้ำสองครั้ง,
  code review จับได้ว่ามีสิ่งที่ Claude ควรรู้อยู่แล้ว หรือคุณพิมพ์คำแก้ไขเดิมในแชทสองเซสชันติดกัน
- **ให้เจาะจงพอที่จะตรวจสอบได้** "Run `pnpm run build` before pushing" ดีกว่า "make sure it
  builds" กฎที่คลุมเครือไม่สามารถพิสูจน์ได้ว่าเท็จ ดังนั้น Claude จึงบอกไม่ได้ว่าตัวเองทำตามหรือไม่
- **ย้ายขั้นตอนออกไป เก็บแต่ข้อเท็จจริงไว้** เวิร์กโฟลว์หลายขั้นตอน ("วิธีตัด release") ควรอยู่ใน
  skill ที่โหลดตามต้องการ — ไม่ใช่ใน CLAUDE.md ที่โหลดทุกเซสชันไม่ว่าคุณจะต้องใช้หรือไม่
- **ใช้ `CLAUDE.local.md` ที่ถูก gitignore** สำหรับอะไรก็ตามที่เป็นส่วนตัว — URL sandbox ในเครื่อง
  ของคุณ, ข้อมูลทดสอบ — ที่ไม่ควรรั่วไหลเข้า context ของเพื่อนร่วมทีมผ่าน git
- **อย่าแย่งงานกับ auto memory** ถ้า Claude คอยเรียนรู้เรื่อง build quirk เดิมซ้ำๆ เองอยู่แล้ว
  ปล่อยให้ auto memory เก็บมันไว้ สงวน CLAUDE.md ไว้กับสิ่งที่คุณตัดสินใจเองอย่างตั้งใจ ไม่ใช่สิ่งที่
  Claude ค้นพบเอง
