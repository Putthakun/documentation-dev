## design pattern คืออะไร

design pattern คือ **วิธีแก้ปัญหาที่มีชื่อเรียก** สำหรับปัญหาที่เกิดซ้ำ ๆ ในเรื่องการสร้าง การประกอบ หรือการสื่อสารระหว่าง object คุณค่าส่วนใหญ่อยู่ที่ชื่อ: การพูดว่า "นั่นคือ Strategy" สื่อสารรูปแบบทั้งหมดได้ในคำเดียว

แคตตาล็อกคลาสสิก (หนังสือ "Gang of Four") เขียนขึ้นสำหรับ C++ และ Java ที่มี class, constructor และ inheritance **Go ไม่มีสิ่งเหล่านั้นเลย** ดังนั้นหลาย pattern จึงมีหน้าตาแตกต่างไปโดยสิ้นเชิงในภาษานี้ และบาง pattern ก็หายไปเลยเพราะภาษาจัดการให้อยู่แล้ว:

| Pattern แบบคลาสสิก | ใน Go |
|---|---|
| Strategy | เป็นแค่ interface หรือ function value |
| Iterator | `range` และ `iter.Seq` ตั้งแต่ Go 1.23 |
| Template Method | Composition ด้วย embedded struct หรือ func field |
| Abstract Factory | constructor ที่ return interface |
| Builder | Functional options |

<Note title="Pattern คือคำศัพท์ ไม่ใช่ checklist" type="warning">
  ความผิดพลาดที่พบบ่อยที่สุดกับหัวข้อนี้คือการมอง pattern เป็นสิ่งที่ต้อง *เพิ่มเข้าไป*
  แท้จริงแล้วมันเป็นชื่อของรูปแบบที่เกิดขึ้นเองเมื่อปัญหาจริงผลักดันให้คุณไปถึงจุดนั้น
  โค้ด Go ที่เต็มไปด้วย `AbstractUserFactoryProvider` แย่กว่าโค้ดที่มีแค่ function ธรรมดา ๆ
  หยิบ pattern มาใช้เมื่อคุณรู้สึกถึงความเจ็บปวดที่มันช่วยขจัดออกไป — ไม่ใช่ก่อนหน้านั้น
</Note>

## Creational patterns

เกี่ยวกับการสร้าง object

### Factory

function ที่ return ค่าที่พร้อมใช้งาน โดยซ่อนว่าคุณได้ concrete type อะไรมา Go ไม่มี constructor ดังนั้น **ทุกฟังก์ชัน `NewX` ก็เป็น factory อยู่แล้ว** — pattern นี้จะน่าสนใจจริง ๆ ก็ตอนที่ return type เป็น interface และการเลือกเป็นแบบ dynamic

```go showLineNumbers title="internal/storage/storage.go"
type Storage interface {
    Save(ctx context.Context, key string, data []byte) error
    Load(ctx context.Context, key string) ([]byte, error)
}

// The factory: caller says what it wants, not how to build it.
func New(kind string, cfg Config) (Storage, error) {
    switch kind {
    case "s3":
        return newS3Storage(cfg)
    case "local":
        return newLocalStorage(cfg.Dir)
    case "memory":
        return newMemoryStorage(), nil
    default:
        return nil, fmt.Errorf("unknown storage kind %q", kind)
    }
}
```

```go showLineNumbers
// main.go — the concrete type is decided by config, not by code.
store, err := storage.New(os.Getenv("STORAGE_KIND"), cfg)
```

นี่คือที่เดียวที่การ return interface ถูกต้อง แม้จะขัดกับคำแนะนำทั่วไปที่ว่า "accept interfaces, return structs" — เพราะประเด็นทั้งหมดของมันคือ caller ต้องไม่รู้ concrete type

### Builder → functional options

Builder แบบคลาสสิกจะ chain การเรียก method เพื่อประกอบ object ที่ซับซ้อน สิ่งที่เทียบเท่าแบบ idiomatic ใน Go คือ **functional options pattern** และมันดีกว่าจริง ๆ: มันเป็น variadic ดังนั้นการเพิ่ม option ใหม่จะไม่ทำให้ caller เดิมพังเลย

ปัญหาที่มันแก้ — constructor ที่โตขึ้นเรื่อย ๆ:

```go showLineNumbers
// The pain: every new setting breaks every caller.
func NewServer(addr string, timeout time.Duration, maxConns int, tls bool) *Server
```

วิธีแก้:

```go showLineNumbers title="internal/server/server.go"
type Server struct {
    addr     string
    timeout  time.Duration
    maxConns int
    logger   *slog.Logger
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option {
    return func(s *Server) { s.timeout = d }
}

func WithMaxConns(n int) Option {
    return func(s *Server) { s.maxConns = n }
}

func WithLogger(l *slog.Logger) Option {
    return func(s *Server) { s.logger = l }
}

func New(addr string, opts ...Option) *Server {
    s := &Server{
        addr:     addr,
        timeout:  30 * time.Second,      // sensible defaults
        maxConns: 100,
        logger:   slog.Default(),
    }
    for _, opt := range opts {
        opt(s)
    }
    return s
}
```

```go showLineNumbers
srv := server.New(":8080")                              // defaults are fine
srv := server.New(":8080", server.WithTimeout(5*time.Second))
srv := server.New(":8080",
    server.WithTimeout(5*time.Second),
    server.WithMaxConns(500),
)
```

<Note title="ทำไมวิธีนี้ดีกว่า config struct" type="success">
  struct `Config` เป็นคำตอบทั่วไปอีกแบบ และก็ใช้ได้ดี Options ชนะในสองเรื่อง: field
  ที่เป็น zero-value ใน struct แยกไม่ออกจาก "ไม่ได้ตั้งค่า" (`Timeout: 0` ตั้งใจหรือเปล่า?)
  และ options สามารถ validate หรือคำนวณได้ — `WithTLS(certFile)` โหลด cert แล้ว return error ได้
  ใช้ config struct สำหรับ 10+ ตัวตั้งค่าที่มาจากไฟล์ทั้งหมด ใช้ options สำหรับ library API
</Note>

### Singleton

instance เดียว ใช้ร่วมกัน ใน Go ให้ใช้ `sync.Once` — ปลอดภัยภายใต้ concurrency และเป็นแบบ lazy:

```go showLineNumbers
var (
    poolOnce sync.Once
    pool     *pgxpool.Pool
)

func Pool() *pgxpool.Pool {
    poolOnce.Do(func() {
        pool = mustConnect()
    })
    return pool
}
```

<Note title="เลือกส่ง dependency เข้าไปแทน" type="danger">
  Singleton คือ global state ที่ใส่หมวก มันทำให้ test ขึ้นกับลำดับการรัน (คุณสลับ pool
  ต่อ test ไม่ได้) ซ่อน dependency (ไม่มีอะไรใน signature ของ function บอกว่ามันแตะฐานข้อมูล)
  และกลายเป็นคอขวดสำหรับ parallel test

  สร้างสิ่งนั้นครั้งเดียวใน `main.go` แล้ว **ส่งลงไป** แทน สงวน `sync.Once` ไว้สำหรับ
  resource ระดับ process จริง ๆ อย่าง metrics registry เท่านั้น
</Note>

## Structural patterns

เกี่ยวกับการประกอบชิ้นส่วนเข้าด้วยกัน

### Adapter

ทำให้ type ที่มีอยู่แล้ว satisfy interface ที่มันไม่ได้ถูกเขียนมาสำหรับ เพราะ interface ของ Go ถูก satisfy โดย implicit adapter จึงมักเป็นแค่ struct ห่อบาง ๆ — หรือบางทีก็ไม่ต้องมีอะไรเลย

```go showLineNumbers
// We need this. A third-party client has SendMail(to, subj, body string) error.
type Notifier interface {
    Notify(ctx context.Context, userID, message string) error
}

// The adapter: bridges the gap without touching either side.
type EmailNotifier struct {
    client *sendgrid.Client
    users  UserLookup
}

func (n *EmailNotifier) Notify(ctx context.Context, userID, message string) error {
    email, err := n.users.EmailFor(ctx, userID)
    if err != nil {
        return fmt.Errorf("looking up email for %s: %w", userID, err)
    }
    return n.client.SendMail(email, "Notification", message)
}
```

standard library ใช้เทคนิคนี้อยู่ตลอด — `http.HandlerFunc` คือ adapter ที่แปลง function ธรรมดาให้เป็น `http.Handler`:

```go showLineNumbers
type HandlerFunc func(ResponseWriter, *Request)

func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) {
    f(w, r)                    // the entire adapter
}
```

### Decorator

ห่อบางสิ่งด้วยสิ่งที่มี interface เดียวกัน แล้วเพิ่มพฤติกรรมเข้าไป นี่คือวิธีที่ **middleware** ทำงาน และน่าจะเป็น pattern ที่คุณจะใช้บ่อยที่สุดใน backend ของ Go

```go showLineNumbers title="internal/httpapi/middleware.go"
func WithLogging(next http.Handler, log *slog.Logger) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)
        log.Info("request",
            "method", r.Method,
            "path", r.URL.Path,
            "duration", time.Since(start))
    })
}

func WithAuth(next http.Handler, verify TokenVerifier) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        claims, err := verify(r.Header.Get("Authorization"))
        if err != nil {
            http.Error(w, "unauthorized", http.StatusUnauthorized)
            return                                  // stop the chain
        }
        ctx := context.WithValue(r.Context(), userKey, claims.UserID)
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}
```

```go showLineNumbers
// Compose them. Each layer is independently testable.
handler := WithLogging(WithAuth(mux, verify), logger)
```

รูปแบบเดียวกันนี้ใช้ได้นอกเหนือจาก HTTP ด้วย — decorator ของ `Store` ที่เพิ่ม caching หรือ retry:

```go showLineNumbers
type CachedStore struct {
    inner Store                  // same interface
    cache *lru.Cache
}

func (c *CachedStore) GetByID(ctx context.Context, id int64) (*User, error) {
    if u, ok := c.cache.Get(id); ok {
        return u.(*User), nil
    }
    u, err := c.inner.GetByID(ctx, id)
    if err != nil {
        return nil, err
    }
    c.cache.Add(id, u)
    return u, nil
}
```

ไม่มีอะไรที่ใช้ `Store` ต้องเปลี่ยนแปลง นั่นคือประเด็นทั้งหมดของมัน

### Facade

จุดเข้าใช้งานที่เรียบง่ายจุดเดียวครอบ subsystem ที่ยุ่งเหยิงหลายตัว มีประโยชน์เมื่อ workflow หนึ่งแตะ service สี่ตัว และ caller ทุกตัวไม่เช่นนั้นจะต้องรู้จักทั้งสี่ตัว

```go showLineNumbers
// Facade: callers just say "check out". They don't know about
// payments, inventory, email, or the order of operations.
type CheckoutService struct {
    orders    OrderStore
    payments  PaymentGateway
    inventory InventoryService
    email     Notifier
}

func (c *CheckoutService) Checkout(ctx context.Context, cart *Cart) (*Order, error) {
    if err := c.inventory.Reserve(ctx, cart.Items); err != nil {
        return nil, fmt.Errorf("reserving stock: %w", err)
    }
    charge, err := c.payments.Charge(ctx, cart.UserID, cart.Total())
    if err != nil {
        c.inventory.Release(ctx, cart.Items)        // compensate
        return nil, fmt.Errorf("charging: %w", err)
    }
    order, err := c.orders.Create(ctx, cart, charge.ID)
    if err != nil {
        return nil, fmt.Errorf("creating order: %w", err)
    }
    c.email.Notify(ctx, cart.UserID, "Order confirmed")
    return order, nil
}
```

ความเสี่ยงคือ facade อาจค่อย ๆ กลายเป็น god object โดยไม่รู้ตัว จำกัดมันให้ทำแค่ orchestration — เรียงลำดับการเรียกและจัดการความล้มเหลว — แล้วผลักกฎที่แท้จริงลงไปไว้ที่ subsystem แต่ละตัว

## Behavioral patterns

เกี่ยวกับวิธีที่ชิ้นส่วนต่าง ๆ คุยกัน

### Strategy

สลับ algorithm ได้ตอน runtime ใน Go นี่ *เป็นแค่ interface* ซึ่งเป็นเหตุผลว่าทำไมมันแทบไม่รู้สึกเหมือนเป็น pattern เลย

```go showLineNumbers title="internal/payment/payment.go"
type Method interface {
    Charge(ctx context.Context, amountCents int64) (*Receipt, error)
    Name() string
}

type StripeMethod struct{ client *stripe.Client }
type PayPalMethod struct{ client *paypal.Client }
type PromptPayMethod struct{ client *promptpay.Client }

// The context doesn't care which one it holds.
type Processor struct {
    methods map[string]Method
}

func (p *Processor) Pay(ctx context.Context, method string, amount int64) (*Receipt, error) {
    m, ok := p.methods[method]
    if !ok {
        return nil, fmt.Errorf("unsupported payment method %q", method)
    }
    return m.Charge(ctx, amount)
}
```

การเพิ่ม provider ตัวที่สี่หมายถึงการเพิ่มไฟล์หนึ่งไฟล์กับ map entry หนึ่งรายการ ไม่มีอะไรเดิมเปลี่ยนแปลง — นั่นคือ Open/Closed Principle ในทางปฏิบัติ ซึ่งครอบคลุมอยู่ในหน้า [SOLID Principles](/docs/solid-principles)

เมื่อ strategy มี method เดียวเท่านั้น ให้ข้าม interface ไปแล้วใช้ **function type** แทน:

```go showLineNumbers
type PricingRule func(order *Order) int64

var rules = map[string]PricingRule{
    "standard": func(o *Order) int64 { return o.Subtotal },
    "member":   func(o *Order) int64 { return o.Subtotal * 90 / 100 },
    "bulk":     func(o *Order) int64 {
        if o.Quantity >= 100 {
            return o.Subtotal * 80 / 100
        }
        return o.Subtotal
    },
}
```

### Observer

สิ่งหนึ่งเปลี่ยนแปลง แล้วมีหลายสิ่งต้องรับรู้ ภายใน process เดียว channel ของ Go ทำให้เรื่องนี้เป็นธรรมชาติ:

```go showLineNumbers
type Event struct {
    Name    string
    Payload any
}

type Bus struct {
    mu   sync.RWMutex
    subs map[string][]chan Event
}

func NewBus() *Bus {
    // The map must exist — writing to a nil map panics.
    return &Bus{subs: make(map[string][]chan Event)}
}

func (b *Bus) Subscribe(name string) <-chan Event {
    b.mu.Lock()
    defer b.mu.Unlock()
    ch := make(chan Event, 16)              // buffered: a slow subscriber won't block the publisher
    b.subs[name] = append(b.subs[name], ch)
    return ch
}

func (b *Bus) Publish(e Event) {
    b.mu.RLock()
    defer b.mu.RUnlock()
    for _, ch := range b.subs[e.Name] {
        select {
        case ch <- e:
        default:
            slog.Warn("dropping event, subscriber full", "event", e.Name)
        }
    }
}
```

<Note title="Observer ภายใน process เดียวไม่รอด restart" type="warning">
  วิธีนี้ใช้ได้ดีสำหรับ cache invalidation หรือ metrics แต่ **ไม่** เหมาะกับสิ่งที่ต้อง
  เกิดขึ้นแน่นอน — ถ้า process ตายระหว่าง publish กับ handle event ก็หายไปเลย
  event ที่ต้องข้าม process หรือห้ามสูญหายควรอยู่บน broker จริงพร้อม transactional outbox
  ตามที่กล่าวไว้ใน [Software Architecture Patterns](/docs/software-architecture-patterns)
</Note>

### Command

ห่อ request ไว้เป็นค่า (value) เพื่อให้มันถูกจัดคิว, retry, log หรือ undo ได้ นี่คือหน้าตาของ background job:

```go showLineNumbers
type Command interface {
    Execute(ctx context.Context) error
    Name() string
}

type SendEmailCommand struct {
    To      string
    Subject string
    Body    string
    mailer  Mailer
}

func (c SendEmailCommand) Name() string { return "send_email" }
func (c SendEmailCommand) Execute(ctx context.Context) error {
    return c.mailer.Send(ctx, c.To, c.Subject, c.Body)
}

// A worker treats every job identically — retries, logging, and
// metrics are written once, not per job type.
func (w *Worker) Run(ctx context.Context, queue <-chan Command) {
    for cmd := range queue {
        if err := retry(ctx, 3, cmd.Execute); err != nil {
            slog.Error("command failed", "name", cmd.Name(), "err", err)
        }
    }
}
```

## ตัวอย่างจริง: notification สามรูปแบบ

ระบบ notification ที่เริ่มต้นแบบง่าย ๆ แล้วเติบโตขึ้น — แสดงให้เห็น Strategy, Decorator และ Factory ทำงานร่วมกัน

```go showLineNumbers title="internal/notify/notify.go"
package notify

// Strategy: each channel is one implementation.
type Sender interface {
    Send(ctx context.Context, to, message string) error
}

type EmailSender struct{ /* ... */ }
type SMSSender struct{ /* ... */ }
type SlackSender struct{ /* ... */ }

// Decorator: retries, wrapping any Sender.
type RetrySender struct {
    inner    Sender
    attempts int
}

func (r RetrySender) Send(ctx context.Context, to, msg string) error {
    var err error
    for i := 0; i < r.attempts; i++ {
        if err = r.inner.Send(ctx, to, msg); err == nil {
            return nil
        }
        if i == r.attempts-1 {
            break                                   // no point sleeping after the last try
        }
        select {
        case <-ctx.Done():
            return ctx.Err()
        case <-time.After(time.Duration(1<<i) * time.Second):   // backoff
        }
    }
    return fmt.Errorf("after %d attempts: %w", r.attempts, err)
}

// Decorator: metrics, also wrapping any Sender.
type MeteredSender struct {
    inner Sender
    kind  string
}

func (m MeteredSender) Send(ctx context.Context, to, msg string) error {
    start := time.Now()
    err := m.inner.Send(ctx, to, msg)
    sendDuration.WithLabelValues(m.kind, statusOf(err)).Observe(time.Since(start).Seconds())
    return err
}

// Factory: assemble the stack from config.
func NewSender(kind string, cfg Config) (Sender, error) {
    var base Sender
    switch kind {
    case "email":
        base = &EmailSender{ /* ... */ }
    case "sms":
        base = &SMSSender{ /* ... */ }
    case "slack":
        base = &SlackSender{ /* ... */ }
    default:
        return nil, fmt.Errorf("unknown notifier %q", kind)
    }
    return MeteredSender{inner: RetrySender{inner: base, attempts: 3}, kind: kind}, nil
}
```

ทุกชิ้นส่วนทดสอบแยกกันได้ retry กับ metrics ถูกเขียนแค่ครั้งเดียวแทนที่จะเขียนสามครั้ง และการเพิ่ม channel ตัวที่สี่แค่แตะ `switch` case เดียว ไม่มี inheritance ไม่มี framework — มีแค่ interface กับ struct

## Best practices

- **ปล่อยให้ pattern เกิดขึ้นเอง** เขียนเวอร์ชันตรงไปตรงมาก่อน แล้วค่อย refactor ไปสู่ pattern เมื่อความซ้ำซ้อนหรือความแข็งทื่อปรากฏขึ้นจริง ๆ
- **เลือก composition มากกว่า inheritance** — Go ไม่ให้ทางเลือกอื่นอยู่แล้ว ซึ่งกลายเป็นข้อดี
- **interface ที่มี method เดียวมักจะดีกว่าถ้าทำเป็น type `func`** ประกาศ type น้อยลง และ closure ก็ได้มาฟรี
- **return concrete type, accept interface** — ยกเว้นจาก Factory ที่การซ่อน concrete type คือประเด็นหลัก
- **หลีกเลี่ยง Singleton** wire dependency ใน `main.go` แล้วส่งลงไป
- **Decorator ต้องไม่เปลี่ยน interface** ถ้าตัวห่อต้องการ method เพิ่ม มันก็ไม่ใช่ decorator แล้ว
- **อย่าตั้งชื่อ type ตามชื่อ pattern** `RetrySender` บอกว่ามันทำอะไร ส่วน `SenderDecoratorImpl` ไม่บอกอะไรเลย
