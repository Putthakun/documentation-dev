## Arrays — fixed size, rarely used directly

An array's length is part of its type: `[3]int` and `[4]int` are different types. Arrays are **values** — assigning one copies it.

```go showLineNumbers
var a [3]int          // [0 0 0]
b := [3]string{"x", "y", "z"}
c := [...]int{1, 2, 3} // compiler counts the elements

d := b     // full copy, not a reference
d[0] = "changed"
fmt.Println(b[0]) // still "x"
```

You'll rarely declare arrays directly. They exist mainly as the storage that slices point at.

## Slices — what you'll actually use

A slice is a dynamically-sized view into an array. Under the hood it's a small struct with three fields:

<Mermaid chart="graph LR
  subgraph Slice Header
  P[ptr]
  L[len = 3]
  C[cap = 5]
  end
  P --> A
  subgraph Backing Array
  A[10] --- B[20] --- C2[30] --- D[unused] --- E[unused]
  end" />

- **ptr** — where the slice starts in the backing array
- **len** — how many elements it currently contains (`len(s)`)
- **cap** — how many it can hold before needing to grow (`cap(s)`)

```go showLineNumbers
var s []int              // nil slice — len 0, cap 0, but usable
s = append(s, 1)

t := []int{1, 2, 3}      // literal
u := make([]int, 0, 10)  // len 0, cap 10 — preallocated
v := make([]int, 5)      // len 5, cap 5 — [0 0 0 0 0]
```

### append and growth

`append` returns a **new slice header** — you must assign the result:

```go showLineNumbers
s = append(s, 4)            // always reassign
s = append(s, 5, 6, 7)      // multiple values
s = append(s, other...)     // append another slice
```

When `len` would exceed `cap`, Go allocates a bigger backing array (roughly doubling) and copies everything over. That's why preallocating matters in hot paths:

```go showLineNumbers
// Good: one allocation instead of repeated grow-and-copy
results := make([]User, 0, len(rows))
for _, row := range rows {
    results = append(results, toUser(row))
}
```

### Slicing

```go showLineNumbers
s := []int{0, 1, 2, 3, 4, 5}

s[1:4]   // [1 2 3]  — from index 1 up to (not including) 4
s[:3]    // [0 1 2]
s[2:]    // [2 3 4 5]
s[:]     // whole slice
```

<Note title="Slices share the backing array" type="danger">
  Slicing does **not** copy data — both slices point at the same memory. Mutating one is visible
  through the other:

  ```go
  original := []int{1, 2, 3, 4, 5}
  part := original[1:3]   // [2 3]
  part[0] = 99
  fmt.Println(original)   // [1 99 3 4 5] — original changed!
  ```

  The same applies to `append` when spare capacity exists: it writes into the shared array and can
  silently overwrite data another slice can see. When you need independence, copy explicitly:

  ```go
  independent := make([]int, len(part))
  copy(independent, part)
  ```
</Note>

This also matters for function arguments: passing a slice copies the *header*, not the data — so the function can modify your elements, but appending inside it won't be visible to the caller.

## Maps

An unordered key–value store. Keys must be comparable (no slices, maps, or functions as keys).

```go showLineNumbers
// Always create with make or a literal — a nil map panics on write
m := make(map[string]int)
n := map[string]int{"alice": 30, "bob": 25}

m["alice"] = 30          // set
age := m["alice"]        // get
delete(m, "alice")       // delete
count := len(m)          // size
```

### Missing keys and the comma-ok idiom

Reading a missing key returns the value type's **zero value**, not an error — so you can't tell "missing" from "present but zero" without the second return value:

```go showLineNumbers
age := m["nobody"]          // 0 — but does the key exist?

age, ok := m["nobody"]
if !ok {
    // definitely not present
}
```

### Iteration order is random

```go showLineNumbers
for key, value := range m {
    // Order differs on EVERY run — this is deliberate, to stop
    // anyone depending on it.
}

// If you need deterministic order, sort the keys:
keys := make([]string, 0, len(m))
for k := range m {
    keys = append(keys, k)
}
sort.Strings(keys)
for _, k := range keys {
    fmt.Println(k, m[k])
}
```

### Sets

Go has no set type. The idiom is a map with an empty-struct value, which uses zero bytes:

```go showLineNumbers
seen := make(map[string]struct{})
seen["alice"] = struct{}{}

if _, ok := seen["alice"]; ok {
    // present
}
```

<Note title="Maps are not safe for concurrent use" type="warning">
  Concurrent reads are fine, but a concurrent read and write will crash your program with a
  "concurrent map writes" fatal error that `recover` cannot catch. Protect maps with a
  `sync.RWMutex`, or use `sync.Map` for specific append-heavy workloads. Run tests with
  `go test -race` to catch this.
</Note>

## Best practices

- **Preallocate with `make([]T, 0, n)`** when you know roughly how many elements you'll add.
- **Always reassign the result of `append`.**
- **Copy explicitly** when a slice must not share memory with its source — especially before storing it somewhere long-lived.
- **Return empty slices, not nil,** from functions when the caller will marshal to JSON (`nil` encodes as `null`, empty encodes as `[]`). Otherwise `nil` is fine and idiomatic.
- **Use the comma-ok idiom** whenever "missing" and "zero" mean different things.
- **Never rely on map iteration order.** Sort the keys when order matters.
