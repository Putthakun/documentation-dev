## Structs

Struct จัดกลุ่ม field ที่เกี่ยวข้องกันเข้าเป็น custom type Go ไม่มี class — struct บวก method คือวิธีที่คุณจำลองสิ่งต่าง ๆ

```go showLineNumbers
type User struct {
    ID        string
    Name      string
    Email     string
    Age       int
    CreatedAt time.Time
}
```

### การสร้าง struct

```go showLineNumbers
// Field names — always prefer this form
u := User{
    ID:   "u_123",
    Name: "alice",
    Age:  30,
}

// Positional — fragile: adding a field breaks every call site. Avoid.
u := User{"u_123", "alice", "a@example.com", 30, time.Now()}

// Zero value — every field gets its own zero value
var u User

// Pointer to a new struct
u := &User{Name: "alice"}
```

<Note title="ใช้ field name เสมอ" type="success">
  Positional struct literal จะพังแบบเงียบ ๆ เมื่อมีคนเรียง field ใหม่หรือแทรก field เข้าไป
  Named field ยังให้คุณข้าม field ที่ไม่สนใจได้ และมันอธิบายตัวเองที่จุดเรียกใช้อยู่แล้ว
</Note>

### Struct tags

Tag คือ metadata string ที่ library อ่านผ่าน reflection — มักใช้บ่อยที่สุดสำหรับ mapping JSON และ database:

```go showLineNumbers
type User struct {
    ID        string    `json:"id" db:"id"`
    Name      string    `json:"name" db:"name"`
    Email     string    `json:"email,omitempty" db:"email"`
    Password  string    `json:"-"`                    // never serialized
    CreatedAt time.Time `json:"created_at" db:"created_at"`
}
```

- `json:"id"` — ใช้ `id` เป็น JSON key แทน `ID`
- `omitempty` — ไม่รวม field นี้เลยเมื่อมันเป็น zero value
- `json:"-"` — ไม่รวม field นี้เลย **ใช้กับข้อมูลลับทุกตัว**: password, token, internal flag

## Methods

Method คือ function ที่มี **receiver** — value ที่มันถูกผูกไว้ด้วย Go ไม่มี `this` หรือ `self`; คุณต้องตั้งชื่อ receiver เอง

```go showLineNumbers
type Rectangle struct {
    Width, Height float64
}

// Value receiver — operates on a copy
func (r Rectangle) Area() float64 {
    return r.Width * r.Height
}

// Pointer receiver — can modify the original
func (r *Rectangle) Scale(factor float64) {
    r.Width *= factor
    r.Height *= factor
}

rect := Rectangle{Width: 3, Height: 4}
fmt.Println(rect.Area())  // 12
rect.Scale(2)             // Go automatically takes &rect for you
fmt.Println(rect.Area())  // 48
```

## Value เทียบกับ pointer receiver

นี่คือการตัดสินใจที่ทำให้ Go beginner ทุกคนสะดุด และมันสร้าง bug ที่คอมไพล์ผ่านได้อย่างสมบูรณ์:

<Mermaid chart="graph TD
  A[Method needs to modify the receiver?] -->|Yes| P[Pointer receiver]
  A -->|No| B[Is the struct large,<br/>or does it contain a mutex?]
  B -->|Yes| P
  B -->|No| V[Value receiver]
  P --> C[Be consistent:<br/>if any method uses a pointer,<br/>use pointers for ALL methods]
  V --> C" />

```go showLineNumbers
type Counter struct {
    count int
}

// BUG: value receiver gets a copy — the increment is thrown away
func (c Counter) IncrementBroken() {
    c.count++
}

// Correct: pointer receiver modifies the original
func (c *Counter) Increment() {
    c.count++
}

var c Counter
c.IncrementBroken()
fmt.Println(c.count)  // 0 — silently did nothing
c.Increment()
fmt.Println(c.count)  // 1
```

<Note title="เลือกแบบใดแบบหนึ่งแล้วสม่ำเสมอในแต่ละ type" type="warning">
  การผสม receiver คนละแบบใน type เดียวกันทำให้เกิดปัญหาแฝงเรื่องการ satisfy interface: `*T`
  เข้าถึงได้ทั้ง value และ pointer method แต่ `T` ธรรมดามีแค่ value method — ดังนั้น
  `T` อาจไม่ satisfy interface ที่ `*T` satisfy ได้ แนวทางมาตรฐานคือ: **ถ้า method ใด
  method หนึ่งต้องใช้ pointer receiver ให้ทุก method ของ type นั้นใช้ pointer receiver**
</Note>

## Embedding — composition ไม่ใช่ inheritance

การ embed type โดยไม่ตั้งชื่อ field จะ promote field และ method ของมันขึ้นมาที่ struct ภายนอก:

```go showLineNumbers
type Base struct {
    ID        string
    CreatedAt time.Time
}

func (b Base) Age() time.Duration {
    return time.Since(b.CreatedAt)
}

type User struct {
    Base           // embedded — no field name
    Name  string
}

u := User{
    Base: Base{ID: "u_123", CreatedAt: time.Now()},
    Name: "alice",
}

fmt.Println(u.ID)     // promoted from Base
fmt.Println(u.Age())  // method promoted too
fmt.Println(u.Base.ID) // the explicit path still works
```

นี่คือ composition: `User` **มี** `Base` มันไม่ได้ inherit จาก Base ไม่มี polymorphism ในที่นี้ — `User` ไม่สามารถแทนที่ `Base` ได้ Interface ต่างหากที่ให้ความสามารถนั้น และมันคือหัวข้อถัดไป

<Note title="อย่า overuse embedding" type="warning">
  Embedding จะ promote API ทั้งหมดของ type ที่ embed มา รวมถึง method ที่คุณอาจไม่อยากเปิดเผยด้วย
  Named field (`base Base`) มักจะชัดเจนกว่า สงวน embedding ไว้สำหรับความสัมพันธ์แบบ
  "is-composed-of" จริง ๆ และสำหรับ embed interface ใน test double
</Note>

## Constructors

Go ไม่มี constructor keyword convention คือใช้ function `New...` ที่ return type นั้น:

```go showLineNumbers
func NewUser(name, email string) (*User, error) {
    if name == "" {
        return nil, errors.New("name is required")
    }
    return &User{
        ID:        uuid.NewString(),
        Name:      name,
        Email:     email,
        CreatedAt: time.Now(),
    }, nil
}
```

ใช้ constructor เมื่อการสร้าง object ต้องมีการ validate, ตั้งค่า default หรือ generate field ถ้า zero value ใช้งานได้อยู่แล้ว ให้ข้าม constructor ไปเลย — นั่นเป็น idiomatic กว่า

## แนวทางปฏิบัติที่ดี

- **ใช้ named field ใน struct literal เสมอ**
- **เพิ่ม `json:"-"` ให้กับทุก field ที่ sensitive** เพื่อไม่ให้มันรั่วไหลเข้าไปใน response หรือ log ได้เลย
- **สม่ำเสมอกับ receiver type** ในทุก method ของ type เดียวกัน
- **ทำให้ struct มีจุดเน้นชัดเจน** Struct ที่มี 25 field มักจะเป็น struct หลาย ๆ ตัวสวมเสื้อคลุมตัวเดียวกัน
- **ตั้งชื่อ receiver ด้วย 1-2 ตัวอักษร** ที่มาจาก type (`r Rectangle`, `u *User`) — เป็น idiomatic Go และไม่ใช้ `this` หรือ `self` เด็ดขาด
- **เลือก composition มากกว่า embedding chain ที่ลึก** Go ตั้งใจไม่มี inheritance; อย่าพยายามสร้างมันขึ้นมาใหม่
