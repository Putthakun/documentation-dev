## Creating a table

```sql showLineNumbers
CREATE TABLE users (
    id         BIGSERIAL PRIMARY KEY,
    email      TEXT NOT NULL UNIQUE,
    name       TEXT NOT NULL,
    is_active  BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Each column is `name TYPE [constraints]`. Constraints (`NOT NULL`, `UNIQUE`, `PRIMARY KEY`) are covered on the [next page](/docs/sql-postgresql-basics/constraints-keys) — this page is about the types.

## Choosing types

### Text

PostgreSQL has `TEXT`, `VARCHAR(n)`, and `CHAR(n)`. In PostgreSQL they're all the same underlying type with the same performance:

```sql showLineNumbers
name  TEXT NOT NULL,              -- use this
email VARCHAR(255) NOT NULL,      -- no faster, and the 255 is arbitrary
code  CHAR(10)                    -- pads with spaces. Avoid.
```

<Note title="Just use TEXT" type="success">
  `VARCHAR(n)` is not an optimization in PostgreSQL — it only adds a length check. If you need a
  real limit, a `CHECK` constraint expresses it more honestly and is easier to change later.
  `CHAR(n)` blank-pads values and causes surprising comparison behavior; there's no good reason to
  use it.
</Note>

### Numbers

| Type | Use for |
|---|---|
| `INTEGER` (`int4`) | Ordinary whole numbers up to ~2.1 billion — counts, quantities |
| `BIGINT` (`int8`) | IDs, and anything that might exceed 2 billion |
| `NUMERIC(p, s)` | **Money and anything requiring exactness.** Arbitrary precision, no rounding error |
| `REAL` / `DOUBLE PRECISION` | Scientific/approximate values only |
| `BIGSERIAL` | Auto-incrementing `BIGINT` — shorthand for an identity column |

<Note title="Never store money in a float" type="danger">
  `DOUBLE PRECISION` cannot represent `0.1` exactly, so amounts drift as you add them. Two safe
  options:

  ```sql
  price_cents INTEGER NOT NULL,     -- store minor units (integer cents)
  price NUMERIC(12, 2) NOT NULL     -- or exact decimal
  ```

  Integer cents is often simplest for a backend, since it maps cleanly to an `int64` in Go and
  removes decimal handling entirely. Pick one convention and apply it everywhere.
</Note>

### Dates and times

```sql showLineNumbers
created_at TIMESTAMPTZ NOT NULL DEFAULT now(),  -- use this for events
birth_date DATE,                                 -- a calendar date, no time
duration   INTERVAL                              -- a span of time
```

<Note title="Always TIMESTAMPTZ, never TIMESTAMP" type="warning">
  `TIMESTAMP` (without time zone) stores a wall-clock reading with no indication of *where* — so
  the same value means different moments depending on who reads it. `TIMESTAMPTZ` stores an
  absolute point in time (internally UTC) and converts on display. Anything representing "when
  something happened" should be `TIMESTAMPTZ`. Use plain `DATE` only for genuine calendar dates
  like a birthday.
</Note>

### Booleans, UUIDs, and JSON

```sql showLineNumbers
is_active BOOLEAN NOT NULL DEFAULT true,
id        UUID NOT NULL DEFAULT gen_random_uuid(),
metadata  JSONB,                    -- binary JSON: indexable, use this over JSON
tags      TEXT[]                    -- native array column
```

`JSONB` is genuinely useful for data whose shape varies, but don't reach for it as an excuse to skip schema design — you lose type checking and constraints. Structured data belongs in columns.

### Enums

Two reasonable approaches:

```sql showLineNumbers
-- Option A: TEXT with a CHECK — easy to extend, most common
status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),

-- Option B: a real enum type — stricter, but adding values requires ALTER TYPE
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');
status order_status NOT NULL DEFAULT 'pending',
```

`TEXT` + `CHECK` is usually the better default: changing the allowed set is a simple constraint change, and it maps to a plain `string` in Go.

## Auto-incrementing IDs

```sql showLineNumbers
-- Classic and still fine
id BIGSERIAL PRIMARY KEY,

-- Modern SQL-standard equivalent (PostgreSQL 10+), slightly preferred
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

-- UUIDs — good when IDs must be generated by clients or be unguessable
id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
```

Sequential `BIGINT` IDs are compact and index well. UUIDs avoid coordination between services and don't leak how many records you have, at the cost of more storage and worse index locality. For a first project, `BIGSERIAL` is a perfectly good default.

## Changing tables

```sql showLineNumbers
ALTER TABLE users ADD COLUMN phone TEXT;
ALTER TABLE users DROP COLUMN phone;
ALTER TABLE users RENAME COLUMN name TO full_name;
ALTER TABLE users ALTER COLUMN name SET NOT NULL;
ALTER TABLE users ALTER COLUMN email TYPE VARCHAR(320);

DROP TABLE users;              -- fails if other tables reference it
DROP TABLE IF EXISTS users;
```

<Note title="ALTER TABLE takes locks" type="danger">
  On a production table, some `ALTER` operations lock the table and block all reads and writes
  while they run — which on a large table can mean an outage. Adding a nullable column is fast;
  adding a `NOT NULL` column with a default, or changing a column's type, may rewrite the whole
  table. Never run these by hand in production. Use versioned migrations and check the locking
  behavior first — see [Migration Strategies](/docs/migration-strategies).
</Note>

## Best practices

- **`TEXT` for strings, `TIMESTAMPTZ` for times, `NUMERIC` or integer cents for money.** These three defaults prevent most data-type regret.
- **Name tables plural and lowercase** (`users`, `orders`), columns `snake_case`. Consistency matters more than the specific choice, but this is the PostgreSQL norm — and unquoted identifiers are folded to lowercase anyway.
- **Add `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` to every table.** You will eventually want it, and backfilling it later is painful.
- **Prefer `NOT NULL` unless a column genuinely has an "unknown" state.** Nullable columns push complexity into every query that touches them.
- **Never change schema by hand in production** — always through a migration file that's reviewed and version-controlled.
