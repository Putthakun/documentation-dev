## การสร้างตาราง

```sql showLineNumbers
CREATE TABLE users (
    id         BIGSERIAL PRIMARY KEY,
    email      TEXT NOT NULL UNIQUE,
    name       TEXT NOT NULL,
    is_active  BOOLEAN NOT NULL DEFAULT true,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

แต่ละคอลัมน์มีรูปแบบ `name TYPE [constraints]` ส่วน constraint (`NOT NULL`, `UNIQUE`, `PRIMARY KEY`) จะอธิบายใน[หน้าถัดไป](/docs/sql-postgresql-basics/constraints-keys) — หน้านี้จะเน้นเรื่อง type

## การเลือก type

### Text

PostgreSQL มี `TEXT`, `VARCHAR(n)` และ `CHAR(n)` ซึ่งใน PostgreSQL ทั้งสามเป็น type เดียวกันภายใน มี performance เท่ากันหมด:

```sql showLineNumbers
name  TEXT NOT NULL,              -- use this
email VARCHAR(255) NOT NULL,      -- no faster, and the 255 is arbitrary
code  CHAR(10)                    -- pads with spaces. Avoid.
```

<Note title="ใช้ TEXT ไปเลย" type="success">
  `VARCHAR(n)` ไม่ได้ช่วยเพิ่ม performance ใน PostgreSQL — มันแค่เพิ่มการตรวจสอบความยาวเข้ามาเท่านั้น
  ถ้าต้องการจำกัดความยาวจริงๆ การใช้ `CHECK` constraint จะสื่อความหมายได้ตรงกว่าและแก้ไขทีหลังง่ายกว่า
  ส่วน `CHAR(n)` จะเติมช่องว่างต่อท้ายค่าและทำให้พฤติกรรมการเปรียบเทียบแปลกๆ ไม่มีเหตุผลที่ดีให้ใช้เลย
</Note>

### ตัวเลข

| Type | ใช้สำหรับ |
|---|---|
| `INTEGER` (`int4`) | เลขจำนวนเต็มทั่วไปถึงประมาณ 2.1 พันล้าน — จำนวนนับ, ปริมาณ |
| `BIGINT` (`int8`) | ID และอะไรก็ตามที่อาจเกิน 2 พันล้าน |
| `NUMERIC(p, s)` | **เงินและอะไรก็ตามที่ต้องการความแม่นยำ** ความละเอียดตามต้องการ ไม่มีความคลาดเคลื่อนจากการปัดเศษ |
| `REAL` / `DOUBLE PRECISION` | ใช้กับค่าทางวิทยาศาสตร์/ค่าประมาณเท่านั้น |
| `BIGSERIAL` | `BIGINT` ที่เพิ่มค่าอัตโนมัติ — เป็นทางลัดของ identity column |

<Note title="ห้ามเก็บเงินเป็น float เด็ดขาด" type="danger">
  `DOUBLE PRECISION` ไม่สามารถเก็บค่า `0.1` ได้อย่างแม่นยำ ดังนั้นเมื่อบวกหลายๆ ครั้งค่าจะเพี้ยนไปเรื่อยๆ
  มีสองทางเลือกที่ปลอดภัย:

  ```sql
  price_cents INTEGER NOT NULL,     -- store minor units (integer cents)
  price NUMERIC(12, 2) NOT NULL     -- or exact decimal
  ```

  การเก็บเป็นสตางค์แบบ integer มักจะง่ายที่สุดสำหรับ backend เพราะแมปกับ `int64` ใน Go ได้พอดี
  และตัดปัญหาการจัดการ decimal ออกไปเลย เลือกแบบใดแบบหนึ่งแล้วใช้ให้สม่ำเสมอทั้งระบบ
</Note>

### วันที่และเวลา

```sql showLineNumbers
created_at TIMESTAMPTZ NOT NULL DEFAULT now(),  -- use this for events
birth_date DATE,                                 -- a calendar date, no time
duration   INTERVAL                              -- a span of time
```

<Note title="ใช้ TIMESTAMPTZ เสมอ ห้ามใช้ TIMESTAMP" type="warning">
  `TIMESTAMP` (ไม่มี time zone) เก็บค่าเวลาแบบนาฬิกาธรรมดาโดยไม่บอกว่า *อยู่ที่ไหน* — ดังนั้นค่าเดียวกัน
  อาจหมายถึงช่วงเวลาที่ต่างกันขึ้นอยู่กับว่าใครเป็นคนอ่าน ส่วน `TIMESTAMPTZ` เก็บจุดเวลาที่แน่นอน
  (เก็บเป็น UTC ภายใน) แล้วค่อยแปลงตอนแสดงผล อะไรก็ตามที่แทน "เหตุการณ์เกิดขึ้นเมื่อไหร่" ควรเป็น
  `TIMESTAMPTZ` ส่วน `DATE` ธรรมดาใช้เฉพาะกับวันที่ตามปฏิทินจริงๆ เช่นวันเกิด
</Note>

### Boolean, UUID และ JSON

```sql showLineNumbers
is_active BOOLEAN NOT NULL DEFAULT true,
id        UUID NOT NULL DEFAULT gen_random_uuid(),
metadata  JSONB,                    -- binary JSON: indexable, use this over JSON
tags      TEXT[]                    -- native array column
```

`JSONB` มีประโยชน์จริงๆ สำหรับข้อมูลที่รูปร่างเปลี่ยนแปลงได้ แต่อย่าใช้มันเป็นข้ออ้างเพื่อข้ามการออกแบบ schema —
เพราะคุณจะสูญเสียการตรวจสอบ type และ constraint ไป ข้อมูลที่มีโครงสร้างชัดเจนควรอยู่ในคอลัมน์ปกติ

### Enum

มีสองแนวทางที่สมเหตุสมผล:

```sql showLineNumbers
-- Option A: TEXT with a CHECK — easy to extend, most common
status TEXT NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),

-- Option B: a real enum type — stricter, but adding values requires ALTER TYPE
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');
status order_status NOT NULL DEFAULT 'pending',
```

`TEXT` + `CHECK` มักเป็นตัวเลือกเริ่มต้นที่ดีกว่า: การเปลี่ยนชุดค่าที่อนุญาตทำได้ง่ายแค่แก้ constraint และมันแมปกับ `string` ธรรมดาใน Go

## ID แบบเพิ่มอัตโนมัติ

```sql showLineNumbers
-- Classic and still fine
id BIGSERIAL PRIMARY KEY,

-- Modern SQL-standard equivalent (PostgreSQL 10+), slightly preferred
id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,

-- UUIDs — good when IDs must be generated by clients or be unguessable
id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
```

ID แบบ `BIGINT` เรียงลำดับกะทัดรัดและทำ index ได้ดี ส่วน UUID ช่วยหลีกเลี่ยงการต้องประสานงานระหว่าง service และไม่เปิดเผยว่าคุณมีข้อมูลกี่รายการ แต่ต้องแลกกับพื้นที่จัดเก็บที่มากขึ้นและ index locality ที่แย่ลง สำหรับโปรเจกต์แรกๆ `BIGSERIAL` เป็นค่าเริ่มต้นที่ดีเพียงพอแล้ว

## การเปลี่ยนแปลงตาราง

```sql showLineNumbers
ALTER TABLE users ADD COLUMN phone TEXT;
ALTER TABLE users DROP COLUMN phone;
ALTER TABLE users RENAME COLUMN name TO full_name;
ALTER TABLE users ALTER COLUMN name SET NOT NULL;
ALTER TABLE users ALTER COLUMN email TYPE VARCHAR(320);

DROP TABLE users;              -- fails if other tables reference it
DROP TABLE IF EXISTS users;
```

<Note title="ALTER TABLE จับ lock" type="danger">
  บนตารางที่ใช้งานจริง คำสั่ง `ALTER` บางแบบจะล็อกตารางและบล็อกทั้งการอ่านและเขียนระหว่างที่รันอยู่ —
  ซึ่งบนตารางขนาดใหญ่อาจหมายถึงระบบล่มไปช่วงหนึ่ง การเพิ่มคอลัมน์ที่ nullable ทำได้เร็ว
  แต่การเพิ่มคอลัมน์ `NOT NULL` ที่มีค่า default หรือการเปลี่ยน type ของคอลัมน์ อาจต้องเขียนตารางทั้งตารางใหม่
  ห้ามรันคำสั่งเหล่านี้ด้วยมือบน production เด็ดขาด ใช้ migration ที่มีเวอร์ชันควบคุมและตรวจสอบพฤติกรรมการ lock ก่อนเสมอ —
  ดู [Migration Strategies](/docs/migration-strategies)
</Note>

## แนวทางปฏิบัติที่ดี

- **ใช้ `TEXT` สำหรับข้อความ, `TIMESTAMPTZ` สำหรับเวลา, `NUMERIC` หรือสตางค์แบบ integer สำหรับเงิน** ค่าเริ่มต้นทั้งสามนี้ช่วยป้องกันปัญหาเรื่อง data type ส่วนใหญ่ได้
- **ตั้งชื่อตารางเป็นพหูพจน์และตัวพิมพ์เล็ก** (`users`, `orders`) ส่วนคอลัมน์ใช้ `snake_case` ความสม่ำเสมอสำคัญกว่าตัวเลือกที่แน่ชัด แต่นี่คือธรรมเนียมของ PostgreSQL — และ identifier ที่ไม่ใส่ quote จะถูกแปลงเป็นตัวพิมพ์เล็กอยู่แล้ว
- **เพิ่ม `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` ให้ทุกตาราง** ในที่สุดคุณจะต้องใช้มัน และการเติมย้อนหลังทีหลังนั้นยากลำบากมาก
- **เลือกใช้ `NOT NULL` เป็นหลัก เว้นแต่คอลัมน์นั้นมีสถานะ "ไม่ทราบค่า" จริงๆ** คอลัมน์ที่ nullable จะเพิ่มความซับซ้อนให้กับทุก query ที่แตะมัน
- **ห้ามเปลี่ยน schema ด้วยมือบน production** ต้องผ่าน migration file ที่มีการรีวิวและควบคุมเวอร์ชันเสมอ
